# Work Item: Feature

Title: webapp v0
Issue: issuelink

Depends on: 0139–0143 (unified daemon API, terminal hub, engine/frontend protocol and worker views). This item follows 0158 in the README implementation order; its screen/action inventory must use the completed contracts of other TUI/API features it presents. Reconcile changes before implementation.

## Summary:
- Build a Next.js, installable, offline-capable PWA at https://awman.prettysmart.dev. Cloudflare serves only the app shell. The user's local awman daemon runs every session, agent, command, workflow and terminal; there is no cloud relay, daemon or agent.
- Recreate the TUI's features and workflow behavior with responsive web controls and applicable keyboard shortcuts. The webapp is a presentation frontend for the daemon engine, not another implementation of awman business logic.
- Keep session content and daemon traffic between the browser and the user's machine. The serving Worker records page loads and privacy-preserving daily/monthly distinct-IP estimates from the initial document request, with no client telemetry or stored visitor identifiers.
- A browser cannot use 0140's owner-only Unix socket/named pipe. Extend the daemon's `daemon.network` API to support multiple named listeners, each with its own bind address, transport, feature allowlist and browser origins. This lets worker use a public TLS listener while engine stays on loopback HTTP, without a browser gateway or another daemon process. Webapp v0 works only on the machine running the daemon; remote-machine browser access is later work. It may be split into transport/security, web UI and deployment work items, but all gates must pass before webapp v0 is complete.

## User Stories

### User Story 1:
As a: developer using awman

I want to:
open local sessions in a browser and perform the same tab, command, workflow, config and agent actions as in the TUI

So I can:
move between terminal and browser without changing how my work behaves.

### User Story 2:
As a: developer who needs local HTTP access

I want to:
enable selected daemon features on a loopback-only HTTP interface while other features can use separate network listeners, and see `awman config set` steps to enable the engine when the webapp cannot find it on the expected port

So I can:
use browser and other local HTTP clients without binding the daemon to a wider network.

### User Story 3:
As a: privacy-conscious user

I want to:
install and reopen the webapp when Cloudflare is unavailable, while keeping my session data local

So I can:
continue working with the same-machine daemon and know that the hosted service retains only aggregate page-load and distinct-IP estimates.

### 2. Named daemon network listeners and launch context
- Replace the unreleased 0140 single-listener settings directly in WI0159 with `daemon.network.listeners`, a map keyed by stable listener name. This is a new canonical config shape: do not read, alias, migrate or issue moved-to hints for `daemon.network.enabled`, `.listen`, `.features` or `.tlsSans`. Those old keys become unknown. A named map lets `awman config set daemon.network.listeners.<name>.<field> …` edit one listener without replacing its siblings; a positional array would make indexed edits and removals fragile. Each listener has `enabled`, `listen`, `transport: "tls" | "loopback_http"`, `features`, `tlsSans` and `allowedOrigins` fields. Keep one daemon API route tree and typed handler stack, with feature filtering and authentication evaluated for the listener that received the request. All listener keys are global config rows; `enabled`, `features`, `transport`, `tlsSans` and `allowedOrigins` apply live, and a changed `listen` requires a daemon restart. A transport change on a bound listener reconnects only its clients and reports that effect. `/v1/status` and `awman daemon status` report each listener by name, address, transport, selected features and bind error. One listener's bind failure does not stop another or the owner-only socket/pipe.
- Define a named `default` listener with defaults `enabled: false`, `listen: "127.0.0.1:9876"`, `transport: "tls"` and `features: ["worker"]`. Define a disabled built-in `loopback` listener with `listen: "127.0.0.1:9877"`, `transport: "loopback_http"`, `features: ["engine"]` and `allowedOrigins: ["https://awman.prettysmart.dev", "http://127.0.0.1:3000", "http://localhost:3000"]`. All other listeners default to an empty `allowedOrigins` list. Owners can change either listener's feature list or add more named listeners. Reject duplicate or overlapping binds, including a wildcard and loopback address on the same port. Keep the owner-only Unix socket/named pipe for management and existing API-key authorization for ordinary network clients. For example, both listeners may be enabled with different interfaces and features:

  ```json
  {
    "daemon": {
      "network": {
        "listeners": {
          "default": {
            "enabled": true,
            "listen": "0.0.0.0:9876",
            "transport": "tls",
            "tlsSans": ["awman.example.org"],
            "features": ["worker"]
          },
          "loopback": {
            "enabled": true,
            "listen": "127.0.0.1:9877",
            "transport": "loopback_http",
            "features": ["engine"],
            "allowedOrigins": ["https://awman.prettysmart.dev"]
          }
        }
      }
    }
  }
  ```

- `allowedOrigins` holds exact browser origins, including scheme, host and port, rather than bare domains. It controls CORS and browser-grant issuance for that listener; it is not authentication. The `loopback` default accepts the hosted origin and both local development origins. Explicit overrides must include each desired origin separately: `http://localhost:3000` and `http://127.0.0.1:3000` are distinct. Reject wildcard or `null` entries, paths, userinfo and malformed origins. Browser grants are bound to one allowed origin and one listener, and removal of an origin revokes its grants and live connections. No origin setting relaxes the listener's bind restriction or makes an API key into a browser grant.
- `loopback_http` serves HTTP/WebSocket without TLS only when `listen` is a literal `127.0.0.1` or `[::1]` address. Reject a hostname, wildcard or non-loopback address at validation, reload and bind time. TLS remains mandatory for every non-loopback listener. Until remote-machine engine access has its own review, reject any listener with `engine` in `features` and a non-loopback bind, even if its transport is TLS. This tightens 0140's warning-only rule so a later address change cannot expose the local engine. Browser pairing routes and grants are available only on loopback HTTP listeners that serve engine; ordinary HTTP clients continue to use 0140's API keys. Advertise `web_frontend` only when the browser protocol is implemented, and report listener availability separately from build capabilities.
- Use `awman config set` for setup; add no web-specific daemon subcommand. The hosted webapp's unavailable-engine screen shows this two-line copyable recipe for the built-in `loopback` listener:

  ```sh
  awman config set daemon.features.engine.enabled true
  awman config set daemon.network.listeners.loopback.enabled true
  ```

  If the daemon is stopped, separately show `awman daemon start --background` as the final step. The preset keeps the common case short without replacing a customized feature list or touching a public worker listener. Show `awman daemon status` for diagnostics and explain how to inspect a custom loopback address or bind error. The browser cannot run these owner-side commands itself. A public TLS listener serving worker and the loopback HTTP listener serving engine may run concurrently.
- The hosted webapp targets the expected `http://127.0.0.1:9877` endpoint. Before probing, handle browser loopback permission from a user gesture when required; then use 0140's minimal unauthenticated `/v1/health` and check protocol/capability and engine state after authorization. If the endpoint is unavailable or the engine is off, show the config recipe above and concise terminal instructions; if the listener is ready but no browser grant exists, show a `Connect browser` action that starts the link flow below. Distinguish a reachable incompatible daemon, missing browser grant and denied browser permission when observable. For an inconclusive failed probe, mention a changed port or bind error as possible causes and point to `awman daemon status`; do not claim that the daemon is stopped. Recheck after the user runs the config commands. Custom listener ports remain available to other HTTP clients, but the hosted v0 webapp uses the fixed default port.
- Consolidate linking under one top-level `awman link` command, with no `awman web` group. `awman link <server-url>` retains 0143's worker-link device flow and its existing `--name`, `--label` and `--token` options; `awman link web-<code>` approves a browser link requested on this machine. The URL and prefixed code make the target unambiguous. Replace the unreleased `awman worker link` spelling directly, without a compatibility alias. Reuse the short-code, expiry, polling and rate-limit mechanics between the flows, while keeping their authority and credentials separate: worker linking registers this daemon with a remote work server and stores a server refresh token; browser linking authorizes one browser origin and listener and stores a local revocable grant. Do not attach browser grants to `workServers` or let a worker-link token authenticate browser requests.
- Browser linking starts from a user gesture in the webapp. `POST /v1/browser-links` on an eligible loopback HTTP listener returns a short expiring `web-` code, an opaque request ID, a separate high-entropy polling secret and a polling interval. The browser shows the code and a copyable `awman link web-<code>` command. The daemon assigns the browser engine scope; the client cannot request owner-management or worker authority. The CLI uses the owner-only socket, displays the requesting Origin, listener and assigned scope, and requires explicit confirmation before approving. The browser polls with its request ID and secret in a non-cacheable request body; approval returns a short-lived, origin- and listener-bound browser grant. The displayed code is one-use lookup material, not the browser credential. Store grant metadata only in owner-private daemon storage; keep live browser tokens and the polling secret in browser memory, never in URLs, cookies, localStorage, service-worker caches, logs or Cloudflare responses. Re-link after browser restart if needed. Expose owner-only `browsers.list` and `browsers.delete id=…` actions through `awman daemon api` for grant review and revocation; rate-limit link creation, polling and approval failures. Loopback binding alone is not authentication.
- Gate browser requests and WebSocket upgrades on an exact Origin in that listener's `allowedOrigins`, expected literal loopback Host/address, route/method allowlist, resource ownership and bounded message sizes. Require a valid browser grant except for the minimal health probe and browser-link creation/polling; link routes still require the exact allowed Origin and Host, and polling requires the high-entropy request secret. 0140's health route may serve nonbrowser clients without an Origin and never exposes session data. Browser-origin requests never fall back to API-key authorization. Never send CORS headers to a disallowed Origin. Reject missing/null browser origins on all other routes, DNS rebinding, redirects to another host, wildcard CORS, credentialed cookies, unpaired WebSockets and cross-site form submissions. An allowed Origin is not authentication; all operational browser routes require the grant. Revocation or daemon lock/stop closes live connections. Apply that listener's feature route filtering, with owner-only management routes remaining on the Unix socket/named pipe.
- Browser WebSocket APIs cannot set arbitrary Authorization headers. Specify a one-use, short-lived upgrade ticket obtained through authenticated, non-cacheable fetch and sent as a validated WebSocket subprotocol; never put credentials in query strings. Bind the ticket to grant, route, origin, expiry and single use. The daemon consumes the ticket without echoing it and selects only the actual awman.frontend.v1 or awman.terminal.v1 protocol. Reconnect obtains a new ticket and resynchronizes from snapshot; do not replay an unacknowledged command or answer blindly.
- The 0142 TUI Hello.env contains shell secrets and a browser cannot supply a faithful shell environment. Extend the frontend handshake with a Web kind and daemon-owned opaque launch-context ID. Create launch contexts through an owner-side CLI action from the desired cwd (or a locally configured, canonical allowlisted project root); keep environment/secrets on the host and resolve paths/config through the existing engine code. The browser may select only authorized contexts and never submit arbitrary env, executable path, host command or mount root. Preserve existing approval prompts for host-sensitive operations. Specify default context and new-tab project selection.
- Same-machine access is the v0 browser boundary: the browser connects only to a loopback listener, and browser grants are refused on every non-loopback listener even when that listener serves other features. A phone or another computer cannot reach the desktop daemon through the v0 webapp. Do not add LAN browser access, Cloudflare Tunnel or a relay in this work item; remote-machine access needs its own later design and security review.

### 3. Next.js UI and terminal presentation
- Put the web project in a dedicated web/ package. Build a static, client-rendered Next.js application with no session-dependent SSR, Server Actions, API routes or server-side daemon fetches. Host assets through a Cloudflare Worker at the required domain. The Worker serves the app shell only; browser-to-daemon traffic goes directly to `daemon.network` on loopback. Audit built output and network traffic for accidental cloud requests from session flows.
- Use one typed browser client for awman.frontend.v1 and awman.terminal.v1. Apply InstanceSnapshot then ordered InstanceDeltas; handle sequence gaps, lagged, chunked snapshots, disconnect/reconnect, primary/secondary ownership, first-answer-wins dialogs and terminal-control changes. Follow 0142 instance exit/close semantics; refresh must not duplicate submission or unexpectedly close live work.
- Build responsive layouts from the action matrix: desktop tab bar, execution area, command composer, workflow and git panels; narrow-viewport navigation/sheets with touch targets, readable status and persistent access to the active agent. A narrow viewport does not imply that a separate device can connect in v0. Keyboard shortcuts use a centralized map derived from TUI behavior (for example Ctrl+T/A/D/G/M/O/W, Ctrl+\, Ctrl+, and context-sensitive Ctrl+C/Esc). Respect browser/OS-reserved combinations and focused text inputs; show visible controls and an in-app shortcut list for unavailable keys.
- Render agent TUIs with a browser terminal emulator fed only by terminal-hub snapshot/output frames, preserving colors, cursor, alternate screen, selection, paste, mouse and keyboard input, resize, parallel terminals and reconnect snapshots. Encode input as the protocol expects; resize only while holding the grant, debounce resize and show read-only/take-control state. On touch devices provide a control-key/escape toolbar and paste. Treat agent output, ANSI/OSC, titles, URLs, repo files and command output as untrusted text: no raw HTML, script execution, automatic URL navigation, clipboard writes or download behavior from terminal escape sequences. Only user gestures may open vetted links or write clipboard.
- Evaluate [wterm](https://wterm.dev/) as the first terminal-renderer candidate for the Next.js frontend. Its [React API](https://wterm.dev/react) exposes output writes, input and resize callbacks, and its DOM renderer supports selection and accessible text; compare its built-in core with the optional [Ghostty core](https://wterm.dev/ghostty) against the agent TUI fixtures before pinning a version. Use wterm only for terminal parsing, rendering and input capture: awman's typed browser client owns `awman.terminal.v1`, upgrade tickets, grants, reconnect and snapshot recovery. Do not use wterm's generic WebSocket transport, in-browser shell, Markdown renderer or WebMCP integration for daemon sessions. Supply explicit input callbacks so terminal input is never locally echoed by default; disable WebMCP and automatic clipboard writes, and allow navigation only from vetted links on user gestures. Review wterm's OSC 8 anchors, title/working-directory callbacks, mouse reports and optional graphics against the untrusted-output rules above.
- Preserve dialog order, confirmation wording and outcomes from the engine; render all 0142 DialogRequest variants, including secret input, workflow controls, setup, mount-scope and config editing. Secret fields never enter analytics, persisted browser state or debug traces. A web-native TerminalRelease view stays inside the hub terminal rather than launching a process on the browser device.

### 4. Offline behavior and Cloudflare usage counts
- Ship a versioned manifest, icons and narrowly scoped service worker that precaches only app shell, fonts and static assets after first successful load. Update atomically so an old shell cannot run with incompatible chunks. Never cache daemon HTTP responses, session snapshots, terminal bytes, credentials or user-entered commands in Cache Storage, IndexedDB, localStorage, HTTP caches or the service worker. Mark all daemon HTTP data Cache-Control: no-store. When Cloudflare is unavailable, the installed shell opens and may reconnect directly to a reachable same-machine daemon; explain that first-time offline installation is impossible.
- Count only an initial top-level HTML document request. For each such navigation, increment the UTC day's page-load total and update separate UTC-day and UTC-calendar-month distinct-IP sketches in one strongly consistent [Durable Object](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) transaction. Use [Cloudflare's incoming `CF-Connecting-IP`](https://developers.cloudflare.com/fundamentals/reference/http-headers/) only transiently at the edge: parse and canonicalize the full IPv4 or IPv6 address, compute separate HMAC-SHA-256 values over `day|period|IP` and `month|period|IP` with an application secret, then discard the address. Send only the two HMAC outputs to the Durable Object; never put the address or HMAC outputs in a URL, log, error, response or persistent row. Disable Pseudo IPv4 header overwriting so IPv6 is counted consistently; do not use `X-Forwarded-For` or a client-supplied identifier. If a trustworthy connecting IP is unavailable or invalid, increment page loads but skip distinct-IP updates and track only an aggregate missing-IP count.
- Store only a bounded HyperLogLog register sketch for each open UTC day and month, plus aggregate page-load and missing-IP totals; do not store individual IPs, HMAC digests, cookies, device IDs or request records. Use a fixed, documented sketch precision and small-cardinality correction, test its error, and label daily/monthly results as approximate **distinct IPs**, not unique people. A shared NAT may count many people as one IP; changing IPs may count one person more than once. Keep day and month sketches separate so MAU is not the sum of DAU; the period label in each HMAC input prevents cross-period linkage. After a period closes, retain only its aggregate counts and estimate, delete its sketch, and expire aggregate rows after 13 months. The owner-only review/export returns UTC day and month, page loads, distinct-IP estimate and missing-IP count; it never exports sketches or HMAC values. No browser analytics, beacons, tracking pixels, telemetry endpoint, service-worker background sync or client-to-Worker usage messages. Asset/manifest requests, fully offline loads, daemon traffic and health checks generate no extra records. Disable application-controlled request/analytics logs, including [Workers invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), that retain identifying metadata; document the remaining Cloudflare platform request-metadata boundary honestly.
- Set restrictive CSP (self-hosted, pinned assets only; no third-party scripts, unsafe inline scripts, JavaScript eval or cross-origin embeds), Referrer-Policy no-referrer, appropriate Permissions-Policy and build integrity checks. If the chosen terminal uses WebAssembly, verify it under the production CSP and permit only the narrow `wasm-unsafe-eval` source expression if required; never add general `unsafe-eval`. Predeclare only `http://127.0.0.1:9877` and `ws://127.0.0.1:9877` in connect-src for the hosted v0 webapp. Do not accept custom browser endpoints outside that policy. Verify the production Next.js output works without weakening CSP. Serve no session data in HTML, hydration payloads, redirects or error pages. Pin and review web dependencies and deployment changes.

## Edge Case Considerations:
- **Browser network permissions and mixed content:** Modern browsers may ask before a public HTTPS origin reaches loopback. Support the permission prompt from a user gesture, standard CORS, denied/revoked states and browser-specific failures. Where supported, mark fetch requests with `targetAddressSpace: "loopback"`; the WebSocket constructor has no such option. Verify HTTP and WebSocket loopback access from the deployed HTTPS origin on supported browsers before release; if a browser blocks the required transport, show a specific unsupported-browser error rather than weakening authentication or changing the bind address. See https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access.
- **Daemon absent, listener off, engine off or version mismatch:** Distinguish these states when observable, offer the `awman config set` recipe and repair guidance, and keep the cached shell usable. A daemon restart can invalidate grants, instance IDs or terminal IDs; re-authenticate and resync without attaching to the wrong instance.
- **Multiple tabs and lifecycle:** One primary per instance per 0142; another same-machine browser tab may attach as secondary or create its own instance. Closing/reloading a browser tab follows an explicit web disconnect policy with reconnect grace, then 0142 primary exit behavior. Make the effect visible before destructive close. Backgrounded tabs may suspend sockets without user intent. Competing dialog answers remain first-wins; late answers receive DialogClosed.
- **Offline shell with incompatible daemon:** Show a version error and route to update when Cloudflare returns, without sending commands through an unverified protocol. Cached UI never treats stale state as authority.
- **Resource limits:** Bound terminal scrollback, incoming frames, queues, tab count and render work; use snapshots after lag and virtualize long logs/lists. Malformed frames, rapid resize, huge paste and slow devices fail cleanly without unbounded memory or leaked input grants.
- **Security boundary:** Hostile pages, malicious extensions, compromised served JavaScript, untrusted repo text/agent output, forged Host/Origin and other local processes are explicit threats. Loopback binding and Origin/CORS alone cannot protect the daemon. Pairing, grants, API keys, route scoping, CSP, output sanitization and approvals all need independent review. A compromised authorized origin remains high impact; deployment compromise response must revoke browser grants and remove `engine` from `daemon.network.listeners.loopback.features` or disable that listener, with no claim of absolute prevention.
